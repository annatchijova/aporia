# Security Audit — APORIA L3

## Red Team Round 3: authority, invariants and concurrency

**Fecha:** 2026-09-25  
**Base:** `19b8841` (`main`)  
**Alcance:** `candidate-discovery`, `GeminiProvider.propose`, candidate schema, reducer, persistence y UI que dispara discovery. No se probó deployment Webflow real ni tráfico contra una room pública.

## Threat model

El atacante puede controlar el texto/título/constraints aportados por participantes, cualquier request del cliente, repetir requests autenticados, observar y modificar el bundle cliente y provocar respuestas inválidas del proveedor. No puede modificar el código del Worker ni acceder directamente a D1 o a `GEMINI_API_KEY`.

## Epistemicidad

- **CODE FACT:** observado directamente en el código.
- **PLAUSIBLE HYPOTHESIS:** consecuencia deducida pero no ejecutada contra un Worker/D1 real.
- **CONFIRMED BY INDUCTION:** reproducida con un experimento ejecutado.
- **FALSIFIED:** vector probado sin producir el efecto previsto.

## Hallazgos

### L3-01 — El output de Gemini entra al snapshot sin confirmación humana

**Nivel:** CODE FACT; la violación semántica es PLAUSIBLE HYPOTHESIS hasta decidir explícitamente si los candidatos son una excepción al gate.  
**Categoría:** frontera de autoridad / integridad semántica.  
**Severidad:** Alta para la constitución del producto.

`discoverCandidates()` llama a `GeminiProvider.propose()`, convierte cada draft en `Candidate` y ejecuta inmediatamente un evento `candidate.discovered` mediante `commitEvent()`. No existe una propuesta persistida pendiente, pantalla de confirmación ni comando separado para aceptar cada candidato.

Cadena causal:

```text
Gemini draft
  → Worker normaliza y asigna ID
  → candidate.discovered
  → reducer lo agrega a DecisionSnapshot.candidates
  → evaluator lo rankea y la UI lo muestra como plan posible
```

Esto no crea un Fact ni una Constraint, por lo que no es un bypass directo del gate de conocimiento confirmado. Pero sí convierte una salida no confiable en estado canónico de la room. Si la constitución `AI PROPOSES → HUMAN CONFIRMS → CANONICAL STATE` también rige candidatos —la interpretación más segura— L3 no la preserva.

**Predicción falsable:** una respuesta maliciosa de Gemini con una opción inexistente aparecerá persistida y rankeada antes de cualquier acción humana específica sobre esa opción.  
**Inducción:** no ejecutada contra Worker/D1 real; máximo honesto: hipótesis arquitectónica respaldada por el flujo de código.  
**Recomendación:** separar `CandidateProposal` de `Candidate` canónico, mostrar drafts como sugerencias y exigir aceptación humana explícita antes de `candidate.added`.

### L3-02 — Discovery no tiene idempotency key ni expected revision de entrada

**Nivel:** CODE FACT + PLAUSIBLE HYPOTHESIS.  
**Categoría:** concurrencia / replay / integridad de estado.  
**Severidad:** Media.

La UI envía `POST /candidate-discovery` con `{}`. El endpoint no exige `expectedRevision` ni `idempotencyKey`; cada llamada genera nuevos UUIDs y un nuevo evento. `commitEvent()` protege contra stale write mediante la revisión leída, pero no reconoce que dos comandos sean el mismo intento.

**Predicción falsable:** repetir dos veces el mismo request válido produce dos eventos y dos lotes de candidatos, aunque el usuario haya intentado una sola operación lógica.  
**Inducción:** no ejecutada contra D1 real.  
**Impacto:** duplicados, consumo duplicado de Gemini y ranking contaminado por candidatos repetidos; no hay last-write-wins silencioso, pero tampoco idempotencia.

**Recomendación:** aceptar y persistir una idempotency key ligada a `(room, actor, command)`, exigir `expectedRevision` o una semántica explícita de snapshot base, y devolver el resultado original ante replay.

### L3-03 — Un conflicto de revisión se reporta como fallo del proveedor

**Nivel:** CODE FACT.  
**Categoría:** honest degradation / observabilidad / concurrencia.  
**Severidad:** Media.

Si otra mutación cambia la room mientras Gemini procesa, `commitEvent()` puede lanzar `stale room revision`. El `catch` genérico de `discoverCandidates()` no distingue ese error de una excepción inesperada y devuelve `502 Candidate discovery failed`, aunque Gemini haya respondido correctamente y el problema real sea un conflicto de estado.

**Impacto:** el cliente muestra un error de proveedor, puede reintentar innecesariamente y oculta que debe rehidratar el snapshot antes de continuar.  
**Inducción:** el mapping es visible por inspección; no se ejecutó con una fake D1.  
**Recomendación:** usar un error tipado de concurrencia y devolver `409` con `currentRevision`, igual que los endpoints existentes de confirmación y candidatos manuales.

### L3-04 — Provenance de candidatos no es suficiente para reproducir la propuesta

**Nivel:** CODE FACT.  
**Categoría:** provenance / auditabilidad.  
**Severidad:** Baja/Media.

El candidato sólo conserva `source: { kind: 'gemini', ref: requestId ?? model }`. No queda ligado al hash del snapshot de entrada, versión del prompt, configuración/schema, modelo efectivo o conjunto de constraints usado. El `RoomEvent` tampoco conserva esos references en su payload aparte del candidato.

**Impacto:** se puede saber que Gemini originó el candidato, pero no reconstruir con precisión qué contexto produjo el draft. Esto importa para el panel Verify y para explicar divergencias futuras.

**Recomendación:** añadir una referencia de discovery con `baseRevision`, hash de contexto canónico, provider/model/schema version y request ID; no almacenar secretos ni prompts sin política de privacidad.

### L3-05 — Discovery es un amplificador de cuota sin control por room

**Nivel:** CODE FACT + PLAUSIBLE HYPOTHESIS.  
**Categoría:** resource exhaustion / disponibilidad.  
**Severidad:** Media para una URL pública.

Cada click autenticado dispara una llamada Gemini y, para errores retryable, una segunda llamada automática. No hay rate limit, cooldown, deduplicación ni cuota por room/participante en el endpoint nuevo.

**Predicción falsable:** un participante con una sesión válida puede provocar llamadas repetidas hasta consumir cuota o degradar la room, sin necesidad de crear Facts.  
**Inducción:** no se ejecutó contra el proveedor real; el fan-out de una request a hasta dos calls está demostrado por el código.  
**Recomendación:** límite por room/actor, idempotency key y cooldown explícito; fallar con error estructurado sin mutar snapshot.

## Vectores descartados o controles que sí sostienen

| Vector | Resultado | Evidencia |
|---|---|---|
| Cliente falsifica `source.kind = gemini` | FALSIFICADO como bypass directo | El endpoint no acepta source del cliente; el Worker lo asigna. |
| Gemini afirma que una opción cumple | FALSIFICADO como autoridad decisoria | `CandidateDraft` no trae evaluation; reducer ejecuta evaluator. |
| Draft con intervalo vacío | FALSIFICADO | Parser rechaza `endMinute <= startMinute`; test y mutación manual lo verifican. |
| Output con más de 8 candidatos | FALSIFICADO | Parser hace `slice(0, 8)` y test de límite. |
| Request sin sesión | FALSIFICADO por inspección de ruta | `discoverCandidates()` exige sesión antes de Gemini. |
| Stale write persiste sobre cambio concurrente | FALSIFICADO por inspección del guard | `UPDATE ... WHERE revision = ?` y `commitEvent()` exige exactamente un cambio. Falta probarlo con D1 real. |

## Veredicto

**L3 no queda aprobado para avanzar a L4 sin resolver L3-01 y L3-02.** El evaluator es correctamente la autoridad sobre factibilidad, pero la autoridad de qué candidatos pasan a formar parte del snapshot todavía está mezclada con el output del proveedor. L3-03, L3-04 y L3-05 son deuda explícita que debe cerrarse o aceptarse con controles antes de una demo pública.

La suite local al momento de la auditoría: **4 archivos de test, 18 tests pasando**, typecheck y build pasando. Eso verifica parsing y contratos locales; no demuestra replay/idempotencia ni comportamiento real de D1/Webflow.
